# V3 运维与异常处理手册

适用于当前 V3 实现，整理日期：2026-10-31。本文把日常检查、故障定位、恢复和专项操作集中在一个入口；不改变运行配置，不代表完整生产验收已通过。生产缺口及证据见 [生产就绪清单](production-readiness.md)。

## 使用约定与快速入口

命令默认在仓库根目录的 PowerShell 执行，本机仓库为 `D:\GitHub\EnterpriseRag`。源码模式使用 `backend/.venv-v3/Scripts/python.exe` 和独立配置 `v3.local`。其他机器先切换到自己的仓库路径；不要把本机示例地址当成生产地址。

| 现象 | 直接查看 |
| --- | --- |
| 页面打不开、API 启动失败、健康检查 503 | [启动和数据库](#startup) |
| 登录失败、401／403、修改配置后没有变化 | [身份与配置](#identity) |
| 文档一直处理中、任务积压、Worker 失联 | [任务处理](#jobs) |
| 上传超时、远端结果未知、不能点击重试 | [上传对账](#unknown-upload) |
| 模型能连接但无法回答、断流、回答慢 | [问答与模型](#chat) |
| 原件无法打开或内容校验不一致 | [原件存储](#originals) |
| 底座不能切换或准备清单过期 | [底座切换](#switching) |
| 删除后还显示清理中 | [撤回与清理](#deletion) |
| 有异常但没有收到通知 | [监控与通知](#alerts) |
| 要备份、恢复、升级或回退 | [备份与恢复](#recovery)、[升级与回退](#release) |

### 哪些命令会改变状态

| 操作 | 实际影响 |
| --- | --- |
| `/health/ready`、`operations-status`、读取日志 | 只读检查；CLI 会连接数据库并检查管理员身份 |
| `check-configuration` | 仅检查本地配置形式，不连接外部服务或修改数据库 |
| `inspect-reconciliation` | 读取任务快照，不签收或重传 |
| `monitor --once` | 更新告警状态、清理过期指标；配置通知地址时可能发送消息，不是只读检查 |
| 重启／重新创建服务 | 中断现有请求；新进程重新读取配置，未完成任务依状态恢复或对账 |
| `migrate`、`reconcile-job`、重试、切换、发布 | 修改数据库或触发业务处理，必须按对应流程核对范围 |
| `backup-bundle` | 新建含业务记录及原件的备份目录；持有企业协调锁，可能阻塞同期业务变更 |
| `restore-bundle`、原件回收 | 写入恢复目标或实际删除候选对象；只在隔离目标或核对后的维护范围执行 |

不要使用直接修改任务状态、清空远端 ID、删除数据卷或绕过 `verified` 的方式消除故障。日志、备份、任务快照可能含业务标识或敏感信息，存放在受限目录，不上传公开报告。

## 日常检查与证据采集

### 本机源码运行

```powershell
Set-Location 'D:\GitHub\EnterpriseRag'
$env:PYTHONPATH = 'backend'
Invoke-RestMethod 'http://127.0.0.1:18000/health/ready'
& ./backend/.venv-v3/Scripts/python.exe -m app.v3.cli --env-file v3.local operations-status
Get-Content -LiteralPath ./data-v3/logs/api.err.log -Tail 100
Get-Content -LiteralPath ./data-v3/logs/worker.err.log -Tail 100
```

日志路径仅适用于通过 `tools/v3/start_local.ps1` 启动的进程。另有 `api.out.log`、`worker.out.log` 和 `data-v3/processes.json` 进程记录；手动启动时看对应终端或服务管理器日志。不要执行打印整个 `v3.local` 或全部环境变量的排障命令。

### 容器运行

```powershell
docker compose -f deploy/v3/compose.yaml ps
docker compose -f deploy/v3/compose.yaml logs --tail 100 api worker database
Invoke-RestMethod 'http://127.0.0.1:18000/health/ready'
```

以下仅查询已有运行容器，不会自动创建服务。容器 CLI 使用 `/run/v3.env`，该文件只挂载在 Worker／迁移服务；API 容器没有此挂载。

```powershell
docker compose -f deploy/v3/compose.yaml exec worker python -m app.v3.cli --env-file /run/v3.env operations-status
```

健康检查返回 200 且 `scope=api_database_only`，仅表示 API 可以访问数据库。继续检查 `workers.healthy`、任务变化及一份已授权资料的实际问答，才能确认相关链路恢复。

### 状态字段和告警码

| 字段／告警码 | 含义与处理方向 |
| --- | --- |
| `jobs`、`bindings` | 任务和副本按状态计数；结合具体任务错误判断，数量为 0 不证明所有外部依赖健康 |
| `workers.healthy / stale` | 心跳正常／过期的 Worker 记录数；当前默认每 15 秒上报，超过 60 秒视为过期。旧进程记录可能仍存在，healthy 大于 0 不表示所有旧实例正常 |
| `oldest_queued_seconds` | 已知创建时间的最老排队任务年龄，含计划未来运行的排队任务；不能直接当作应执行任务的等待时间 |
| `oldest_due_seconds` | 已知执行时间已到的排队任务等待时间；历史无创建时间的记录计入 `queued_without_age`，不能推算其真实年龄 |
| `expired_leases` / `expired_worker_leases` | running 任务租约到期，先检查 Worker 与数据库，不手工延长或清除租约 |
| `overdue_queue` | 已知队龄或到期等待达到 300 秒，检查 Worker、限流、远端处理与调度 |
| `worker_heartbeat_missing` | 已有心跳均过期，或有已知年龄的排队任务且无正常 Worker；无任务时未必产生该告警，仍需看 workers |
| `unknown_remote_results` | 存在待对账任务，按上传对账处理 |
| `failed_jobs` | 存在失败任务，逐项核对错误及是否允许重试 |
| `unconfirmed_remote_deletions` | 副本仍在 delete_requested／delete_pending，远端 API 删除尚未确认 |
| `durations` | 最近 24 小时按阶段及结果聚合的次数、总耗时和最大耗时；不是百分位，也不能代表每次请求详情 |
| `alert_delivery` | 告警是否有效、发送状态、尝试次数和下次尝试时间；发送成功不等于有人处理 |

每次故障记录发生／恢复时间（带时区）、运行模式、版本或未提交代码指纹、涉及的知识库／任务编号、状态和已脱敏错误、采取的操作及恢复验证。记录不包含密钥、令牌、完整连接串或非必要正文。

## 按现象排障

<a id="startup"></a>
### 1. 页面打不开、启动失败或健康检查 503

**检查**：先执行上述服务状态、健康检查和日志命令；源码模式再执行本地配置预检：

```powershell
$env:PYTHONPATH = 'backend'
& ./backend/.venv-v3/Scripts/python.exe -m app.v3.cli --env-file v3.local check-configuration
```

**判断**：连接被拒绝通常需要检查 API 进程、端口或入口代理；生产配置缺项会在业务应用创建前停止。未配置数据库时 `/health` 返回 503；已配置应用的 `/health/ready` 返回 503 时检查数据库服务、地址、认证及网络。数据库正常而首页缺失时检查 `frontend/dist` 是否已构建，以及 `V3_FRONTEND_DIR`。

**处理**：按 [生产配置说明](production-configuration.md) 修正字段；确认独立数据库和底座服务确实运行。新环境先按 README 执行受控迁移，不让多个副本同时迁移。已有环境发生迁移错误时先核对版本与备份，不反复运行迁移碰运气。本机启动脚本不会替你启动停止的 Docker 依赖。

**恢复标准**：首页可访问、API 能访问数据库、预检结果符合运行模式，并能通过本人登录和一条实际授权业务请求；健康 200 本身不足以证明底座和模型恢复。

<a id="identity"></a>
### 2. 登录 401／403，或配置修改没有生效

**检查**：浏览器请求是否携带 `Authorization: Bearer ...`；令牌是否过期，`iss`、`aud`、`tenant_id` 与配置一致，`sub` 是否对应启用的本地用户。检查固定 HTTPS 公钥地址能否被 API 访问，公钥轮换后的 `kid` 是否匹配。检查用户角色、组、资料显式拒绝和发布状态。令牌内容不要粘贴到公开解码网站。

**判断**：401 不只表示密码错误，也可能是公钥服务超时、签名或声明不匹配；403 应结合业务提示判断用户停用、操作角色不足或资料无权访问。身份验证成功不自动赋予资料阅读权限。

**处理**：在企业身份服务重新取得正确令牌；由有权限的管理员修正用户映射或资料授权。开发令牌至少 32 字符，只在 development 使用。配置文件通过 `override=False` 加载，已有进程环境变量优先；修正文件后须核对服务管理器／容器实际注入项，且重启 API 和 Worker。

源码模式通过以下命令重载配置。它会终止所记录的 API／Worker 进程树，正在进行的请求会中断，应在维护窗口执行：

```powershell
& ./tools/v3/start_local.ps1 -Restart
```

容器修改 `.env` 或 Secret 后应重新创建相关容器，`restart` 不会重新注入容器环境：

```powershell
docker compose -f deploy/v3/compose.yaml up -d --force-recreate api worker
```

**恢复标准**：目标用户能访问应允许的资料；无权用户、停用用户和已撤权用户仍被拒绝。不要以关闭身份验证、放宽密钥或切换开发模式作为生产恢复手段。

<a id="jobs"></a>
### 3. 文档长期处理中、任务积压或 Worker 失联

**检查**：查看具体任务／副本状态、Worker 心跳、到期等待、过期租约以及 Worker 日志。`queued` 是待调度，`running` 表示已领取；业务版本 ready 与 published 是两个阶段。任务已完成但资料尚未发布时不会自动进入正常问答。

**处理**：先恢复 Worker 的数据库、对象存储和底座连接，再确认处理状态是否继续推进。底座已经接收文件但解析失败时，检查该平台的 Embedding、格式支持、模型额度和日志，不能只测 V3 的回答模型。明确 failed 的 ingest／replicate／delete 可在修复原因后通过工作台重试；重试接口拒绝其他任务类型和远端结果未知状态。维护任务不进入普通重试队列。

**恢复标准**：至少有正常 Worker 心跳，到期任务持续推进，单个样例达到索引 ready；管理员核对授权并发布后可检索。旧失败任务可能继续触发告警，应逐项处理，不靠清空历史计数消除。

<a id="unknown-upload"></a>
### 4. 上传超时，显示 needs_reconciliation

**检查**：查看该任务是否有原件、提交绑定、目标实例和可识别的远端回执。新上传先由 Worker 自动核对；没有提交证据、候选为空／多个、校验值不符或权限不足时会冻结。

**处理**：恢复用于核对的管理凭据和原件读取权限，等待自动对账。仍无法唯一确认时按下文“上传结果未知”的签收流程，由负责人核实具体远端文件。不能通过普通重试重新上传，也不能复制其他资料的远端 ID。

**恢复标准**：远端归属已核实，任务回到可处理队列并最终 ready，记录可审计；恢复过程没有盲目重复提交。ready 后仍需发布，不以签收成功代替可用性验证。

<a id="chat"></a>
### 5. 模型能连接，却无法回答、回答慢或中途断流

**检查**：依次确认资料发布和授权 → 活动底座及索引 → 受限检索 → 精排 → 生成。查看流内 `status / sources / token / done / error` 及 `durations` 阶段统计，结合 API 日志，不以 HTTP 200 判断回答成功。

**判断与处理**：

- “根据现有资料无法回答”可能是没有授权证据，先核对资料与索引，不直接换模型。
- Embedding 由底座负责；V3 回答接口可用不代表平台编码成功。核对底座自己的模型配置、插件、网络、代理和额度。
- 精排不可用时当前流程明确失败；确认模型名、协议、端点及密钥引用，不能把普通对话模型当精排模型。
- 授权或撤回变化应终止当前访问；目录／路由变化在生成前最多重检一次。反复变化时等变更稳定后重新提问，不绕过权限复查。
- SSE 是逐段推送回答的连接。代理应关闭响应缓冲，允许心跳并设置适当超时；当前 API 每约 5 秒发送等待心跳，整体期限 180 秒。没有 done／error 的结束是异常断流。
- 模型空响应、无效引用、超时或网络断开时消息可能标记 failed；不要手工标成 completed。先修复原因，再发起新请求，外部模型调用可能计费。

**恢复标准**：用一条已知有答案且已授权的样例，收到正确来源、正文和 done；重新读取历史仍有权限且状态 completed。再做无权限反例。延迟恢复应对照具体场景与阶段，不拿单文档历史 P95 当所有业务的承诺。

<a id="originals"></a>
### 6. 原件不能读取或提示 SHA-256 校验失败

**检查**：区分身份／授权拒绝、版本映射错误、对象不存在、存储权限／网络问题和内容不一致。SHA-256 是内容校验值，用来判断文件是否发生变化；核对版本保存的对象键及校验值，避免直接覆盖文件。

**处理**：网络或权限问题修复到正确的租户前缀；内容缺失或损坏时从配套备份恢复到隔离目标先核验。当前工作区的旧 `data/` 不自动成为 V3 原件来源。不要改数据库中的校验值来接受未知文件，不能把平台下载副本不经核对就当作主原件。

**恢复标准**：授权用户通过 V3 原件接口读取成功，内容校验一致，无权用户仍不能读取；相关版本、索引和引用能正确对应。

<a id="switching"></a>
### 7. 底座切换失败或提示清单已过期

**检查**：目标实例是否通过当前环境验证，目标处理副本是否 ready，所需格式／能力是否满足，资料、权限或路由是否在准备后变化。

**处理**：修复目标同步失败，变化后重新准备清单，再以当前预期路由修订号激活。回退也执行同一准备与核验，不能恢复旧权限。源平台故障时没有未经准备的自动切换；不要手工改活动路由或伪造资格报告。

**恢复标准**：激活请求通过，活动路由正确，新提问使用已就绪目标并有有效引用，历史权限仍正确。当前开发试运行资格不能替代生产资格。

<a id="deletion"></a>
### 8. 撤回后仍显示远端清理中

**检查**：先核对本地资料已停止使用，再查 delete 任务、副本状态、权限及网络。详情 API 的 401／403、5xx 或超时均不证明已删除。

**处理**：恢复正确集合的管理／删除凭据，允许 Worker 继续轮询；明确失败的已知远端 ID 删除可按工作台规则重试。详情返回 404 的确认应归档在删除任务中。原件回收另按 [回收说明](original-gc.md) 盘点和核对，不与撤回混为一谈。

**恢复标准**：新检索、原件和相关历史已按撤回策略限制；远端 API 不可见有对应回执。要求物理清除时，还要平台、原件、证据与备份各自证明；delete 任务 completed 不能代替这些证明。

<a id="alerts"></a>
### 9. 存在故障，但没有收到告警

**检查**：用只读 `operations-status` 查看 `alerts` 和 `alert_delivery`。`disabled` 表示未启用外部发送，`retrying` 查看尝试次数与下次时间；`delivered` 只说明接收端返回 2xx，不证明企业通知渠道已送达人。

**处理**：在运行配置中设置可信的 `V3_ALERT_WEBHOOK_URL`（接收告警 HTTP 请求的地址），重载 Worker；接收方按 `event_id` 去重。通知客户端不跟随重定向、不继承环境代理；地址必须能从 Worker 直接访问。生产使用可信 HTTPS 接收端。

以下命令会写告警状态，并在已配置地址时实际发送事件，只在已核对接收端的运维演练中运行：

```powershell
$env:PYTHONPATH = 'backend'
& ./backend/.venv-v3/Scripts/python.exe -m app.v3.cli --env-file v3.local monitor --once
```

**恢复标准**：测试故障产生 firing，恢复产生 resolved，实际接收渠道均收到且重复事件不会重复处理。当前仅有本机接收器演练，企业人员通知接入仍待验收；没有告警也不证明系统无故障。

<a id="recovery"></a>
## 备份与恢复

### 备份范围与执行

同时保管 V3 PostgreSQL、原件、平台部署与索引、模型／解析配置及独立密钥。V3 的 `backup-bundle` 仅打包当前租户的业务记录和被版本引用的原件，不包含平台索引、独立密钥、所有孤立对象或整个企业部署；它不能单独作为完整灾备。

在维护窗口限制业务写入，选择已受访问控制的备份父目录。下例路径是示例，执行前替换；输出的末级目录必须不存在。备份可能包含资料正文和会话，不放入仓库或公开报告。

```powershell
$env:PYTHONPATH = 'backend'
$bundlePath = 'D:\V3-Private\backups\tenant-20261031-001'
& ./backend/.venv-v3/Scripts/python.exe -m app.v3.cli --env-file v3.local backup-bundle --output $bundlePath
if ($LASTEXITCODE -ne 0) { throw '备份失败，不能标记为有效备份' }
```

成功输出 `created=true` 和原件数量；目录包含 `manifest.json`、`rows.json` 与 `objects/`。工具核对原件内容，但成功生成不等于可恢复，仍须隔离恢复演练。全库 PostgreSQL 备份另用同版本 `pg_dump --format=custom --file=<受限路径>`；在安全连接配置中提供数据库凭据，不把密码写入共享命令或报告。

### 隔离恢复步骤

1. 准备独立、全新空数据库和新的本机原件目录或空 S3 前缀，不连接生产入口，不启动目标 Worker。保留恢复所需的旧模型、平台、密钥配置和版本记录。
2. 创建独立 `v3.restore.local`，核对数据库和原件目标均为新目标，租户编号与备份一致。已有进程环境变量优先于文件；使用干净的维护终端并核对实际注入配置，不能仅凭文件名判断安全。
3. 不先执行 `migrate` 子命令：它会创建初始租户，恢复命令随后会拒绝非空库。`restore-bundle` 自行建表／迁移并检查全库无租户。
4. 执行下例；这是实际写入新目标的命令，`--confirm-empty-target` 不能替代前面的目标核对。

```powershell
$env:PYTHONPATH = 'backend'
& ./backend/.venv-v3/Scripts/python.exe -m app.v3.cli --env-file v3.restore.local restore-bundle --input $bundlePath --confirm-empty-target
if ($LASTEXITCODE -ne 0) { throw '恢复未完成，保持目标隔离并保留回执' }
```

5. 核对恢复输出的行数和原件数量、关键业务记录、授权／停用用户、版本及原件内容。S3 恢复会保存恢复尝试清单，包含写入未知／已写／已核验状态；失败时可能保留隔离对象，不自动无条件删除，也不覆盖目标重跑。
6. 核对恢复后的保护状态：Worker 旧租约清除，非 completed／cancelled／failed 任务转为 needs_reconciliation；处理中的消息转 failed；底座验证资格清除，切换清单失效，旧心跳和指标不会被当作实时健康。
7. 先在隔离环境恢复／重建平台数据并重新核对绑定、对账任务和运行资格，再受控启动 API 与 Worker。使用授权正例、撤权反例、原件读取和带引用问答验证，确认通知不会误投旧生产渠道。
8. 记录可接受的数据丢失量、实际恢复耗时及负责人签收，批准后才开放业务入口。完整企业灾备仍待实测。

使用原生 `pg_restore --exit-on-error` 恢复全库时同样只写全新目标；该方式不会自动执行上述 bundle 恢复的资格清除和任务冻结，必须单独核对，不能立即启动旧 Worker。

## 升级、重启与回退

1. 保存应用版本或未提交源码指纹、前后端依赖锁、平台镜像内容指纹、数据库版本、模型配置及现行验证报告；准备可恢复的数据库与原件备份。
2. 维护窗口暂停资料写入和对外问答，受控停止旧 API／Worker，避免旧代码与新数据库并行处理。不要使用 `docker compose down -v`，它会删除持久卷。
3. 构建已审阅版本，单一迁移进程执行迁移，再启动 API 和 Worker。容器命令见根 README；独立知识平台不由 V3 Compose 自动升级。
4. 检查配置、数据库、心跳、样例入库／发布／问答、权限反例和告警，再逐步放开流量。镜像构建成功、健康 200 或配置预检通过均不是生产验收。
5. 回退前判断旧代码是否兼容当前数据库和平台状态；不兼容时按配套备份恢复到新目标，而不是只切回旧镜像。底座回退仍走目标同步与切换核验，不能恢复被撤销的权限。

## 专项处理细节

以下保留具体对账字段、删除确认语义与监控实现边界，供按现象排障定位后继续操作。

## 上传结果未知

明确处理失败的未发布草稿可在“知识资料”点击“取消失败草稿”。此操作保留原件和已发布旧版，只停止该草稿的后续任务／同步；取消后须重新准备底座切换。正在运行或结果待对账的任务不可直接取消，避免丢失远端回执。租约失效不会放宽写回检查，Worker 会结束该次处理并继续循环。

任务在远端 POST 前记录 submitting；如果超时或进程退出且无法确定远端结果，会进入 needs_reconciliation。页面不允许盲目重试，避免同一资料变成多份、错误关联他人的平台文档。

新上传现在会在POST前持久化绑定、原件hash和目标实例证据。Worker交替领取正常任务与自动对账任务，只有完整扫描后的唯一匹配候选且原件回读SHA256一致才认领；WeKnora核对绑定元数据，Dify核对唯一上传名并安全解析同源签名地址。不转发API密钥/Cookie，不跟随跳转，不自动重POST。自动恢复使用manage凭据，需具备该知识库的原件读取权限。丢失Dify batch时使用详情中的真实状态和分块数，不能伪造批次。

旧任务缺少提交证据、候选为空/重复、hash不符、权限不足等仍冻结并保留人工签收CLI。2026-10-31网络恢复后，真实故障探针已验证两套各只上传一次，找回丢失回执后索引最终ready；此前因云Embedding连接超时未就绪的失败报告仍保留。运维不得仅清除状态重传或复制其他版本远端ID。

### 签收已确认的上传回执

适用范围：`needs_reconciliation` 的 ingest／replicate 任务，能唯一确定 `submitting` 绑定、已有集合但尚无远端 ID。已知 ID 的状态轮询失败、多个可疑绑定及结果仍不确定的任务保持冻结，不在此入口强行处理。

在仓库根目录 PowerShell 操作，先导出快照到受限的本机运维目录（文件不应提交 Git）：

```powershell
$env:PYTHONPATH = 'backend'
backend/.venv-v3/Scripts/python.exe -m app.v3.cli --env-file v3.local inspect-reconciliation --job <任务ID>
```

保留输出的全部字段，独立核对平台上传记录及文件归属，再添加以下字段到 JSON 报告：

| 字段 | 内容 |
| --- | --- |
| remote_id | 确认属于该原件、该版本和集合的远端文件 ID |
| batch_id | 平台批次 ID；无批次时填写空字符串 |
| approved_by | 实际核对负责人 |
| note | 核对依据和记录编号，不包含正文或密钥 |
| evidence_sha256 | 已归档核对证据文件的 SHA256，小写 64 位十六进制 |

可用 `Get-FileHash -Algorithm SHA256 <证据文件>` 计算校验值，转为小写。证据文件应单独归档，校验值只供事后核对，不能自行证明远端归属。

```powershell
backend/.venv-v3/Scripts/python.exe -m app.v3.cli --env-file v3.local reconcile-job --job <任务ID> --report <签收报告路径>
```

CLI 沿用部署配置的管理员身份，仅供能访问服务器配置的运维人员使用。系统在同一事务内校验快照、原件完整性和重复绑定，保存签收字段及操作者审计；成功后任务进入 queued，由 Worker 在原底座继续轮询、写入授权元数据，完成后仍需手动发布。原件已撤回时仅安排清理，不恢复发布或检索。重复／过期签收被拒绝。

本工具不会通过“未找到文件”的声明重新上传，也不会验证所填远端 ID 的真实内容。错误的人工签收可能关联错误资料，负责人必须完成独立核对；不能以接口成功代替归属证明。此步骤不代表远端物理清理、自动对账或完整生产 G0 已通过。

## 撤回与删除

业务撤回首先更新本地授权和目录，新的检索、原文下载与历史访问立即受限。远端删除请求单独执行；撤回期间迟到的上传回执仍保存并追加清理任务。delete_requested 只表示已请求删除，不表示平台向量、文件及备份都已物理清除。

Worker 现在对已接受的删除请求继续轮询：仅使用对应文档详情接口返回 404 作为远端 API 不可见的证据；401／403、超时、5xx 或错误集合不能确认删除。确认记录保存在删除任务 payload 的 `deletion_confirmations`，包含绑定 ID、时间和 `remote_api_not_found` 依据；副本状态转为 `deleted`。该状态不代表平台文件、向量或备份已物理抹除。未确认时任务每 30 秒重排；失败可在页面重试。已知远端 ID 的删除超时可重试，不按未知上传永久冻结。

两套底座已用全新合成文件完成解析、删除和查询 404 实测，见 `docs/testing/v3/remote-cleanup-2026-10-30.json`。实际物理清理证明、备份保留期限及原件孤立回收仍待完成，生产准入不能把任务 completed 当成所有存储清理完毕。

## 运行状态与告警入口

- `/health/ready`：无鉴权的数据库连通探针，数据库异常返回 503 且不暴露错误细节。200 只说明 API 能访问数据库，不代表 Worker、模型、对象存储或底座都健康，更不代表生产资格通过。
- `/api/v3/operations`：管理员鉴权，按当前企业聚合任务／绑定状态、过期租约、已知到期任务等待秒数及告警代码，不返回正文、远端 ID 或密钥。
- 同一统计也可在服务器执行 `python -m app.v3.cli --env-file v3.local operations-status`。

新增Job.created_at后，`oldest_queued_seconds`表示真实创建年龄；历史记录创建时间不可推导，迁移为0并单独计入`queued_without_age`。`oldest_due_seconds`仍只表示已知计划执行时间的等待，不与创建年龄混淆。Worker即使空闲也独立上报心跳；`workers`给出健康/失联数量，`durations`按固定阶段汇总最近24小时次数、总耗时和最大值，不记录正文，不冒充P95。

Worker入口现同时运行独立心跳、任务循环和监控轮询；数据库短暂故障不会直接结束正常任务监督循环。也可执行 `python -m app.v3.cli --env-file v3.local monitor --once`，或不加`--once`持续监控。配置`V3_ALERT_WEBHOOK_URL`后按持久告警状态投递，仅包含企业、固定告警码、状态和事件ID；失败退避重试，恢复另发事件。接收方应按event_id去重，这是至少一次送达，不能保证恰好一次。默认空值禁用外部投递。

本机合成接收器已真实验证503重试、204送达、去重及恢复事件；企业告警平台尚未提供，真实人员通知未连接。本机重启显式禁用了外部投递。部署负责人需配置HTTPS、可信接收端与真实渠道后演练，不应将带事件标签的本机接收器当作企业通知完成。

原件孤立回收操作与S3版本化约束见 [回收说明](original-gc.md)；不会自动运行或删除历史版本。

## 回退与切换

切换前准备目标索引并核对资料清单、授权修订号和路由修订号；服务端在事务内再次检查。准备期间资料或权限变化会使原清单失效，需要重新准备。回退使用相同检查，不能恢复旧权限。

没有自动故障切换。源平台故障时不使用未经同步和验收的目标，接口明确失败。旧回答引用自有原件，仍按当前权限检查；不依赖原平台的公开文件链接。
