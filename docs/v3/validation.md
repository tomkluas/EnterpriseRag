# V3 部署验证与验收清单

## 1. 当前状态与执行规则

本文件是验收要求，不是通过报告。两套完整 G0 仍未完成；本机真实双向切换和最新局部真实验证已有通过证据，见 [当前生产差距](production-readiness.md) 与 [实施记录](progress.md)。不能以局部诊断或合成样本通过替代完整生产验收。

验证使用独立 Linux 主机或已启动 Docker Linux 引擎的开发机、独立数据库、独立对象存储目录、独立测试账号和凭据。不得连接当前 V2 生产数据或直接复用其密钥。先使用合成资料，再导入经批准的代表性企业样本。

每次报告保存：代码提交、镜像 digest、配置摘要（脱敏）、模型与解析器版本、硬件、数据量、测试输入、预期、实际、请求 ID、结果与必要截图。失败和未执行单独列出。API 成功、单元测试通过、真实模型效果和生产验收不能相互替代。

## 2. G0 底座采用验证

G0 分别验证两套底座事实，并用最小适配器探针验证同一 V3 安全契约。此阶段允许隔离测试代码，不建设完整业务页面。以下阻断项未通过，不启用对应生产底座；另一套通过不代表首版双底座目标完成。以下 2.1—2.3 是 WeKnora 的具体步骤，Dify 对应步骤见 2.5。

### 2.1 环境准备

在测试主机操作：

```bash
git clone --branch v0.9.0 --depth 1 https://github.com/Tencent/WeKnora.git
cd WeKnora
git rev-parse HEAD
docker version
docker compose version
```

提交必须为 `f17ee8a8da901bd658a4cb25f40b5fd41adbfdd7`。若标签指向不同提交，停止并重新核查。按该版本官方 `.env.example` 和配置说明创建测试 `.env`，保存在测试主机，不提交密钥。

固定 WeKnora 应用、UI、DocReader 的版本并记录拉取后的 digest；发布镜像与已审阅提交之间需有可信构建来源。若无法证明镜像对应提交，使用该提交构建并记录产物。不得使用未固定的 latest 得出版本验收结论。

先保留官方 PostgreSQL 检索组合及 DocReader；确认 Redis 队列生效且持久化卷存在。配置 RBAC 开启、沙箱关闭、release 模式，仅内网访问。启用 OCR 所需的解析引擎及模型后，对扫描件单独验证；不能假定安装基础容器就具备全部解析能力。

在测试环境完成官方初始化，创建两个独立平台空间，每个创建测试知识库。为 V3 分别建立 retrieve、ingest 和管理用途凭据；检索 key 限定知识库白名单。验证取不到其他空间、其他知识库以及写接口。

### 2.2 构造反例资料

准备 A、B、C 三份测试文档，分别写入唯一标记和互相矛盾的数字：A 为允许员工甲访问的现行制度，B 为同库中禁止员工甲访问的制度，C 在另一空间中。另准备 A 的旧版、新版、相同文件的索引重建副本、空文件、扫描 PDF、跨页表格和 DOCX 表格。

让 B 的内容与测试问题高度相关，故意比 A 更容易命中。这样可以证明过滤真实生效，而不是“越权文件碰巧没有被检索到”。

### 2.3 WeKnora 独立检索探针

在测试主机设置环境变量 `WK_BASE_URL`、`WK_RETRIEVE_KEY`、`WK_KB_ID`、`WK_ALLOWED_DOC_ID`，不要输出 key。`WK_BASE_URL` 不含 `/api/v1` 后缀。

创建 `request.json`，将文档编号替换成真实测试 ID：

```json
{
  "query_text": "测试资料中的差旅标准是什么？",
  "knowledge_ids": ["替换为A的实际平台文档ID"],
  "match_count": 50,
  "disable_keywords_match": false,
  "disable_vector_match": false,
  "skip_context_enrichment": true
}
```

```bash
curl --fail-with-body --silent --show-error \
  -X POST "$WK_BASE_URL/api/v1/knowledge-bases/$WK_KB_ID/hybrid-search" \
  -H "X-API-Key: $WK_RETRIEVE_KEY" \
  -H 'Content-Type: application/json' \
  --data-binary @request.json > retrieval-response.json
```

成功判断：返回体为预期结构，所有命中的 `knowledge_id` 均为 A，内容没有 B/C 标记；没有调用平台聊天接口也可取得正文和来源。空命中不能作为范围隔离通过，先单独查询 B 确认它可被检索，再查询受限 A。

分开执行关键词路径、向量路径和混合路径。关键词测试设 `disable_vector_match=true`；向量测试设 `disable_keywords_match=true`。每个路径都验证范围，不只测混合路径。

### 2.4 阻断用例矩阵

| 编号 | 在哪里、怎样操作 | 成功标准 | 范围 |
| --- | --- | --- | --- |
| G0-01 | 底座直接检索 A，三条检索路径分别执行 | 结构、正文、来源可用，限定范围不出现 B/C | 底座 |
| G0-02 | 适配器收到空授权列表，记录底座请求计数 | 返回无权／无资料，底座调用数为 0 | 最小适配器 |
| G0-03 | 伪造路径 KB、body 的多库字段、跨空间文档 ID | 底座 key 边界拒绝；适配器不转发客户端平台参数 | 底座＋适配器 |
| G0-04 | 同库 A/B 不同员工权限，B 有更强匹配词 | B 不进入精排、生成、响应、日志或引用 | 适配器＋模型请求捕获 |
| G0-05 | 上传 A 新版本；失败一次，成功一次后发布 | 失败保留旧版；发布前不召回新版，发布后普通问题不召回旧版 | 版本原型 |
| G0-06 | 同一原件在新物理 KB／数据集建索引代次，旧集合继续查询 | 能保留旧代次并建立新代次；平台重复或替换行为不误认领其他版本 | 底座＋映射原型 |
| G0-07 | 处理中文扫描 PDF、跨页表格、DOCX、XLSX | 原文事实保留，来源定位实际可核查；记录逐格式结果 | 真解析引擎 |
| G0-08 | 标记撤回后查询，制造平台删除失败再重试 | 撤回即不可使用，清理失败可见且可恢复 | 业务原型＋底座 |
| G0-09 | 解析过程中停止应用容器再恢复；单独重启 Redis | 最终完成或明确失败且可重试，无永久处理中；无重复发布 | 隔离容器 |
| G0-10 | 模拟上传服务端已接受但响应丢失 | 对账识别既有记录，不盲目重复创建／发布 | 网络故障注入 |
| G0-11 | 生成前和生成中撤权，包括多轮历史和多实例 | 撤权提交后不再派发新资料调用、不再写出新正文，历史被遮蔽 | 并发探针 |
| G0-12 | 分别注入错误／越权文档 ID、缺失映射，以及合法结果的额外图片字段 | 错误／越权 ID 或缺失映射使整次请求失败；合法结果按字段白名单剥离未授权的附加图片信息和链接 | 故障替身＋真 API 对照 |
| G0-13 | 选定模型进行真实 Embedding、精排和生成 | 确认真接口连通、可取消、超时可见；不是全部使用 mock | 模型服务 |
| G0-14 | 大范围授权、多个物理库、不同模型分组 | 全部授权范围得到处理或明确报错，无静默漏批次、混分数 | 规模探针 |

G0-11 的边界：已经发送给外部模型、已显示或已进入传输缓冲区的文本不能撤回，必须准确报告派发、服务端正文写出与撤权提交时间。只在前端停止显示或只做定期轮询，不足以证明服务端按协调边界停止派发和输出。

若 G0-01/03/06 无法满足固定版本契约，须重新评估底座或隔离粒度；G0-04/11 未通过则禁止上线。若某种格式定位不达标，必须在底座能力清单中标记；业务空间要求精确定位时禁止切到不支持的目标，不能用全局静默降级解决。

### 2.5 Dify 独立验证

在另一隔离目录获取官方 Dify 1.18.0，检查 `git rev-parse HEAD` 等于 `50abea97062110044f15d0e03ccecadd9ccc87ca`。按该版本官方部署说明启动，固定存储、解析和模型插件及所有镜像 digest，保存配置摘要。不可把 WeKnora 的 Redis、ParadeDB 配置当作 Dify 的等价部署。

创建独立工作空间、A/B 同数据集文档和另一隔离数据集，配置实际生效的数据集范围 API Key。若需要多个平台工作空间，先核对许可证适用条件。key 的读写分权不沿用 WeKnora 假设，验证内部代理的方法／路径限制。

创建 string 类型的 `v3_binding_id` 字段；通过文档元数据接口为各文档写入唯一绑定标识，读回并验证。使用 [Dify 请求示例](dual-backend.md#4-dify-文档级过滤与入库顺序)，对 `/v1/datasets/{dataset_id}/retrieve` 分别测语义、全文和混合路径；每条都要求元数据过滤在召回前落实，不能只在答案生成后过滤。

除共同 G0 矩阵外，必须覆盖：

- 元数据过滤无匹配、空列表、字段删除、尚未写入、值重复、用户伪造条件；禁止取消过滤重试。
- 凭据跨数据集访问、检索侧调用写接口、响应的 segment.document_id 与业务映射不符。
- 上传 200 返回的 document／batch、indexing-status 的 paused／error／completed、删除 204 空响应体。
- 251 字符的检索问和多轮改写：短检索问可用，原问不丢失，不能无声截断。
- 分块 position 只当作片段顺序；没有原文页码时不得显示假页码。OCR 和逐格式定位能力独立记录。
- 元数据写入失败、上传超时、平台重启和目标存储恢复；不能让未完成授权标识的记录进入 ready。

### 2.6 双向切换验证

在同一个 V3 测试业务知识库中分别建立两套副本，冻结原件和题库。先使用 WeKnora 回答，再准备 Dify 副本并通过权限、版本和能力预检，执行切换，然后验证回到 WeKnora。

切换准备期间注入新版发布、撤回、撤权和任务重试；确认过期清单／水位阻止切换，最新资料补齐后才能执行。目标未完成、任一所需能力不足、任一权限反例失败、路由修订冲突时，服务端必须拒绝 activate。

同时运行旧请求和新请求：每次请求记录底座实例与路由快照；用并发连接验证 activate／发布与模型派发使用同一共享／独占协调边界，切换先提交时不能再用旧路由证据派发生成。已输出请求不混合底座证据，新查询使用新路由，撤权始终继续生效。验证回退不会复活旧权限；源平台不可用时不得自动切到未就绪目标。退役源平台后，旧引用仍从 V3 自有原件经授权打开。

报告分别记录两套 G0、WeKnora → Dify、Dify → WeKnora 四部分。任一 not_run 或阻断失败，不能宣布首版双底座目标完成。

## 3. 上线前完整验收

### 3.1 业务质量

准备至少 200 道带预期答案和原文依据的业务问题；至少 20 份代表性文件。将有答案、无答案、冲突、历史、表格、扫描件、多轮及权限题分别标注，测试集冻结后不因系统答错就改答案。

记录有答案题正确率、重要结论引用支持率、无答案题正确拒答率以及逐格式定位正确率。评分由资料负责人复核，自动评测只辅助。目标值见 [设计第 11 节](design.md#11-初始验收目标)。错误、超时和权限失败不能计为正确拒答。

### 3.2 故障与一致性

在测试环境模拟：业务 Worker 租约过期、重复领取、旧 Worker 晚到写回、平台 429/5xx、网络超时、精排不可用、流式回答中断、发布与删除并发、权限更新与检索并发。确认无越权、无重复发布、无旧租约覆盖、无“失败标成功”。

重建和回退验证应在查询持续进行时执行，并记录一次回答到底使用哪个版本／代次。切换前后答案不得混入不在范围内的新旧资料。

### 3.3 性能与容量

固定主机配置、模型、网络、原件大小、资料数及活动块数。区分冷启动和稳定负载。以 10 个并发会话作为试点起点，记录首段有效回答 P50/P95、完整回答 P95、成功率、各阶段耗时和队列积压；请求至少持续 30 分钟。

分别覆盖小范围检索和大量授权文档场景，报告每次批次数、候选数和权限核验成本。15 秒召回预算或候选处理预算不足时明确失败，不能靠只查部分资料制造性能达标。无法达标则修改设计参数或分组策略并回归。

### 3.4 备份恢复

在另一套隔离环境恢复完整备份。验证原件、版本指针、授权撤回、密钥解密、平台绑定、可检索文档与引用；暂停写入期间生成并核对备份批次清单。

演练底座不可恢复时从原件重建，并测量重建是否超出恢复目标。不能完成时，应采用更完整的底座备份或调整经确认的恢复目标，不能只保留一句“可重建”。

### 3.5 发布准入

资料负责人确认质量，技术负责人确认权限与故障行为，运维负责人确认部署、监控、密钥、备份和回退。报告列明所有未执行项与实质限制。安全阻断项不得标记为“后续优化”。

## 4. 报告格式

每份 JSON 报告至少包含 `run_id`、`started_at`、`finished_at`、`versions`、`environment`、`dataset`、`checks`、`metrics`、`limitations`。每项 checks 保存编号、输入标识、预期、实际、状态（passed/failed/not_run）及证据路径；不保存 API Key、原文敏感内容或完整个人信息。

时间统一记录带时区时间戳。只能根据可观察的请求、日志和测试记录划分阶段耗时；不能把未分类间隔称为模型思考、排队或网络时间。
