# 独立 S3 服务验证

本次脚本 `tools/v3/verify_real_s3.py` 只使用临时 SQLite 和自行启动的回环地址 MinIO；不读取 `v3.local`、现有数据库、业务对象或存储凭据。MinIO 仅作为 S3 协议测试程序，不作为新生产系统的存储选型。该仓库当前已归档。

固定服务源码：官方标签 `RELEASE.2025-09-07T16-13-09Z`，标签对象 `01ce918d8279a20e4706b96a64396146894adee4`，实际提交 `07c3a429bfed433e49018cb0f78a52145d4bedeb`。使用 `git ls-remote https://github.com/minio/minio.git refs/tags/RELEASE.2025-09-07T16-13-09Z` 及对应 `^{}` 查询确认。

构建过程的工具链、模块、编译缓存只位于 `D:\GitHub\EnterpriseRag\.tmp-real-s3-build`，目录 ACL 已移除继承，仅保留当前用户权限；不会修改全局 Go 配置。系统原有 Go 为 `go1.21.5 windows/amd64`，源码需要至少 Go 1.24。

Go 自动下载工具链曾长时间停留在零字节，改用 Windows 原生 HTTPS 下载官方 `https://proxy.golang.org/golang.org/toolchain/@v/v0.0.1-go1.24.0.windows-amd64.zip`（84,855,039 字节）。下载归档 SHA256 为 `99ab85b1a35d8d7dd9e2c676d6dbbeedc6ab42abf7ca1c061179f1f231974d54`，并逐个文件计算 Go 模块目录哈希，与官方 `sum.golang.org` 的 `h1:3Pq4MkdmsP+OJ9fMYl7UkmKBjORjaTJ/nzTt2s+Br+g=` 一致后才解压使用。此处只确认可观察到的传输差异，没有把未分类耗时归因为网络或模型。

机器可读结果以相邻 JSON 为准。脚本包括真实 S3 备份/恢复和读回 hash、非空前缀拒绝恢复、条件 PUT/DELETE 的 HTTP 412、孤立原件清单及执行、删除前并发替换导致的 HTTP 412，以及 Enabled/Suspended 桶拒绝恢复和回收。回收保留期测试显式传入未来八天的 `now`，只验证时间判断和协议，不表示已经实际等待七天。并发替换在真正的条件 DELETE 请求前写入不同内容，HTTP 响应和存储读写均由独立服务产生。

## 实测结论

源码构建成功，二进制 SHA256 为 `fb32a450d037438185511b6bbf7254ede7bcd6cf66997f48ac311fb284d6c0a6`。默认构建未注入发布标识，`--version` 显示 `DEVELOPMENT.GOGET`，因此版本追溯以固定模块提交、构建命令及二进制 SHA256 为准；运行工具链为 Go 1.24.0。

SQLite 与 PostgreSQL 两种组合都实际完成 S3 备份、恢复、读回哈希一致、拒绝覆盖、条件 PUT 412、Enabled/Suspended 桶拒绝恢复及回收。PostgreSQL 组合执行命令：

```powershell
& backend/.venv-v3/Scripts/python.exe tools/v3/verify_real_s3.py --minio .tmp-real-s3-build/bin/minio.exe --source-commit 07c3a429bfed433e49018cb0f78a52145d4bedeb --postgres-env-file v3.local --report docs/testing/v3/real-s3-postgres-2026-10-31.json
```

该命令只读取部署文件中的数据库 URL，严格检查原地址为 `127.0.0.1:18433/enterpriserag_v3`，随后仅连接已有报告中的 `v3_live_` 合成测试库，为五个逻辑目标各建本轮随机 schema；最终五个 schema 均已删除，不查询或修改既有业务表。

真实测试也揭示两个问题，修复前证据保留在 `real-s3-2026-10-31-before-guard.json`：

- MinIO 此固定版本忽略 DELETE 的错误 `If-Match`，返回 204 并删除测试对象。因此 `conditional_delete_supported=false`，整体 `passed=false`，命令返回 1。此处被删除的仅为脚本新建的私有合成对象，不是用户资料。不能把其他 S3 产品的条件删除能力视为已验收。
- 同一未变对象的 LIST 时间带小数，HEAD 时间只到秒，原来严格比较会误拒绝刚生成的回收清单。现按秒比较 S3 时间，同时继续核对 ETag、大小及内容哈希；保留期采用两次观测中更晚的时间，避免提前删除。

修复后的回收执行在任何候选删除前，自建唯一合成探测对象，要求错误 `If-Match` 确实返回 412 且内容未丢失，再以正确 ETag 条件删除并确认探测对象不存在。403、忽略条件、内容丢失、内容变化或无法确认清理均拒绝执行；错误中记录可能残留的探测对象键，没有无条件删除兜底。清单生成仍只读；每次显式执行均重新探测，且第二阶段仍检查桶版本化状态。

最终真实 MinIO 结果为 `restoration_passed=true`、`gc_safely_refused=true`：实际候选 DELETE 请求为 0，候选与被引用原件仍完整。合成探测对象 DELETE 请求为 1，拒绝后盘点残留为 0；最后只通过关闭本轮 MinIO 并删除本轮私有数据目录完成清理。真实支持条件删除服务的 GC 成功执行及并发替换 412 尚未实测；对应客户端调用链由定向 Stubber 回归覆盖，不能表述为真实协议已通过。

相关回归命令：`$env:PYTHONPATH='backend'; & backend/.venv-v3/Scripts/python.exe -m unittest discover -s backend/tests/v3 -p test_orphan_gc.py`，11 个测试通过，含 LIST/HEAD 精度、正常删除/412冲突、忽略条件先拒绝，以及 PUT/DELETE 403、读回丢失/变化和清理不确定等反例。
