## 2. 已证实问题

### 问题 1：[P2，阻断首版切换验收] 切换遗漏尚未发布的版本

位置：`backend/app/v3/domain.py:206` 的 `prepare_switch`，尤其 209 行只收集非空 `current_version`；发布检查在 160—165 行。API 的切换准备入口直接调用该方法，发布入口调用 `publish`；重试接口 `backend/app/v3/api.py:117` 不接受已经 completed 的原入库任务。

触发步骤：

1. 当前底座 A，上传文档并由真实 Worker 流程处理至 ready，尚不发布。
2. 准备并执行到 B 的切换。
3. 在 B 发布上述版本，再次准备 B 索引。

预期：按设计中的新增／更新同步要求，切换应同步该版本、阻止遗漏草稿的切换，或提供明确的目标补建入口，使上传资料能继续正常发布。

实测：切换任务 `total=0`，允许激活 B；发布报“当前底座索引尚未就绪，不能发布”；重新准备后 B 的复制任务与副本仍均为 0。因为草稿没有 `current_version`，会一直被准备清单忽略。需要切回 A 发布后再切换，或额外人工处理；不是原件丢失。

证据来自隔离 SQLite + 实际 Domain／Worker／租约代码；远端上传与状态仅用替身表示“平台正常完成”。未伪称在真实两底座跑过此流程。

### 问题 2：[P2，阻断幂等正确性验收] 幂等键没有校验目标文档

位置：`backend/app/v3/domain.py:103` 的 `receive`，112—114 行只比较内容 SHA256 和空间，没有比较请求的 `document_id`；真实上传 API 在 `backend/app/v3/api.py:75` 将该字段直接传入。

触发步骤：同一空间已有文档 A、B。先用幂等键 K 和内容 X 更新 A，再用 K、相同内容 X 更新 B。

预期：同一幂等键被用于另一个目标，应明确冲突，不能把 B 的操作返回成 A 的成功结果。

实测：第二次没有冲突，返回与 A 完全相同的 `document_id/version_id/job_id`，且返回文档不是 B。内容与空间相同不足以证明是同一逻辑操作。未发现此反例造成越权读取或覆盖 B；已证明的是错误的成功返回及更新遗漏。

### 另有已确认的设计缺口

- `models.py:51` 的 Version 缺少生效区间，`domain.py:243` 的 scope 只读当前版本，尚未实现“按指定历史时间问制度”。
- `domain.py:277` 会把未知结果置为 needs_reconciliation，API 禁止其盲重试是正确的；但 `cli.py` 只有 migrate、worker 和 accept-validation，没有处理对账的闭环。
- `jobs/worker.py:131` 仅记录 delete_requested；不能证明平台存储物理清除。原件孤立对象回收亦未实现。
- Dify 超 250 字符明确拒绝；短检索问改写、多轮检索改写及切换前单次重检尚未实现。这些不能用“失败时不越权”替代功能完成。

上述是代码与调用链确认的缺口，不是新发现的线上事故。它们和缺少模型配置属于不同问题。
