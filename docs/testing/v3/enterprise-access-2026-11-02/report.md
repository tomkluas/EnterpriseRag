范围：当前公司内的组织、角色、成员、资料工作台与管理员问答审计。不增加平台级租户管理。设计和使用步骤见 [企业权限说明](../../../v3/enterprise-access-design.md)。

原始记录：[完整回归输出](backend-unittest.txt)、[PostgreSQL 补跑输出](postgres-unittest.txt)。

初次运行暴露的夹具不匹配已修正：运维用例降级管理员前先创建另一位管理员，以保留最后管理员保护；跨实例用例改用角色授权字段和新的 HTTP 请求结构。修正后上述运行通过。

新增迁移提交前校验机制后，`test_enterprise_access` 再跑 15 项全部通过，包含校验异常时事务回滚。该项是完整回归之后新增的定向验证，不表述为再次运行过全量套件。

覆盖内容包括：

- 多角色资料授权、禁止优先、默认角色继承与资料追加、关闭继承后的规则。
- 角色停用撤权；组织归属不直接授予资料权；资源管理与资料阅读权限分开。
- 组织循环、跨租户角色引用、公司根名称修改权限、最后管理员保护。
- 旧个人与组授权迁移、不因 `role:` 账号前缀或 `group:` 负责人账号扩大权限、重复迁移。
- 管理员和自定义审计角色查看本公司其他成员问答；普通成员禁止；外租户消息禁止；查看详情写审计。
- 流式输出期间另一 API 实例撤权后不再输出资料，历史依赖重新校验；检索分批和网络等待不持有错误的数据库锁。
- 原密码登录、资料版本、任务、知识适配器、原件恢复和监控回归。

独立评审发现并修复了旧 `role:` 账号迁移扩权与继承语义不一致问题，复验两个对应反例通过。

## PostgreSQL 迁移验证

在随机隔离 schema 中模拟旧版表结构，删除新增组织/角色表及新增字段后升级。原资料的个人授权仍只匹配原成员，重复迁移不改变范围；21 张业务表、157 个字段备注与模型一致，问答审计索引存在。隔离 schema 已清理。

本机启用时又在同一迁移事务内对实际数据的 8 组成员/资料访问结果逐对比较，通过后才提交并重启 API/Worker。重启后 `/health/ready`、企业/组织/角色/成员/审计接口均正常；资料规则仅含角色标识。原任务仍为完成 5、失败 3，无运行中任务，未重试旧失败任务。

## 角色删除占用明细补充

角色无法删除时，接口现在一次返回全部成员、知识库和资料引用；弹框展示名称、账号/标识、允许或禁止规则、停用/撤回状态及具体调整位置，不自动移除关联。只查询当前租户，普通成员不能取得占用明细。

`test_role_references` 与 `test_enterprise_access` 共 23 项通过，覆盖多类关联同时返回、外租户信息不泄露、解除引用后可以删除。前端 3 项测试及生产构建通过。本机只读核查显示，两个 admin 历史角色当前均仅被“V3 企业知识库”的默认允许阅读规则引用。

随后增加“使用情况”只读入口，删除前也会自动读取关联，不必提交删除才能查看。`test_role_references` 的 9 项用例通过，前端 3 项测试和构建通过；本机新接口实际返回两个历史角色均为成员 0、知识库 1、资料 0，具体位置为“知识资料 → V3 企业知识库 → 默认角色授权”。未删除角色或取消任何授权。
